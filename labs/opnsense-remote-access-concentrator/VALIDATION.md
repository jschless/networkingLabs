## Native design probe — 2026-09-02

The main orchestrator used a disposable overlay and genuine OPNsense
26.1.6_2 surfaces: WireGuard General, Client, and Server MVC models,
`OPNsense\Firewall\Filter`, `/usr/bin/wg`, native template/configure actions,
and dynamic interface registration. WireGuard was present in the base image;
no plugin installation was necessary.

The probe established this required apply order:

1. persist General and Client peers without instantiating the Server model;
2. in a separate PHP process, persist the Server relation so the 26.1 model
   cache sees the newly saved Client UUIDs;
3. reconfigure `opt1`/`opt2`, reload `OPNsense/Wireguard`, run
   `configctl wireguard configure`, and invoke interface registration;
4. persist the five `opt3` MVC rules and reload PF.

Observed native evidence:

- instance `0` created `wg0` at `10.250.0.1/24` on UDP/51820;
- two distinct ephemeral clients authenticated as `.10/32` and `.20/32`;
- OPNsense installed both peer `/32` routes through `wg0`;
- clients kept `203.0.113.2` through `eth1` while selecting `wg0` only for
  `10.70.10.0/24`;
- developer reached TCP/8443 and TCP/22, contractor reached only TCP/22, and
  both identities were denied from firewall management;
- the active rule order was logged management block, two developer permits,
  contractor jump permit, and logged contractor application block, all with
  reply-to disabled;
- a bounded developer-WAN capture showed public UDP/51820 in both directions
  and no readable tunnel or CORP address;
- disabling only the contractor record reduced live peer inventory to the
  developer; re-enabling it restored two peers without harming developer;
- changing only contractor server ownership from `.20/32` to `.21/32`
  preserved public underlay, a recent handshake, and developer services while
  contractor jump access failed; restoring `.20/32` recovered it.

This probe establishes mechanism and automation feasibility. It does not
replace clean acceptance against the final scripts.

## Main acceptance — 2026-09-07

One clean deployment was used for the answer-free baseline and final
acceptance. The baseline passed 12 incidental/readiness checks and failed all
47 intended configuration, identity, tunnel, route, policy, and service
checks. No learner answer was present before that measurement.

Acceptance results:

- `solution.sh` converged to exactly 59 passes and zero failures. Its one
  deliberate repeat also produced 59/0 while preserving both client keypairs,
  both client configurations, and the concentrator identity.
- A combined extra saved Client, Server, and firewall-object mutation produced
  exactly the three corresponding inventory failures. A mismatched developer
  private key plus full-tunnel client configuration produced exactly the two
  client continuity/configuration failures. A saved and live broad `wg0` rule
  produced exactly the saved- and live-policy inventory failures. Canonical
  state returned to 59/0 after every negative.
- `capture.sh` accepted exactly four bidirectional public UDP/51820 packets
  and exposed neither tunnel nor CORP addresses. A forced interactive INT
  left no host capture file or client `tcpdump` process.
- Two consecutive revocations retained exactly the developer live peer and
  its two services. Two consecutive re-enrollments restored exact 59/0 while
  preserving both client identities.
- `break.sh` produced exactly 56 passes and three failures: saved contractor
  ownership, contractor jump-service access, and live peer ownership. Public
  underlay, both authenticated identities, the recent contractor handshake,
  and developer services remained healthy. Repeated arming retained the same
  focused fault; repeated `repair.sh` invocations restored 59/0 without key
  rotation.
- Forced solution ERR, interactive INT, and direct single-PID TERM paths
  restored the pre-run guest configuration, client keys/configurations,
  WireGuard state, addresses, and routes. The direct TERM returned 143,
  reaped its tracked hold child, and all cases left zero guest/client backup
  directories. Acceptance caught and corrected missing Docker stdin
  attachment and route serialization that initially broke client rollback.
- Forced break ERR and direct single-PID TERM paths restored exact saved and
  live peer ownership. TERM returned 143 and reaped its tracked hold child;
  both paths left zero backup residue and final health remained 59/0.
- Remote `php -l` accepted `configure.php`, `grade-config.php`, and
  `grade-live.php` on genuine OPNsense. Acceptance also corrected explicit
  `opt3` registration, removed an over-broad CORP ingress rule, matched native
  PF UUID labels, and made live grading reject any extra `wg0` rule.
- A forced missing-base startup preflight exited 1 while preserving the
  already-running VM PID and overlay inode; exact health remained 59/0. This
  closed a review finding in pre-start rollback ownership.

During simultaneous sustained developer application/jump traffic and

## Independent review and clean teardown — 2026-09-07

One read-only reviewer examined the complete implementation, documentation,
security posture, exact grading, transaction/signal handling, and lifecycle.
Its initial findings identified preflight cleanup that could remove an
existing VM overlay and the stale pending-acceptance sentence. After both were
fixed and the preflight regression was live-tested, the same reviewer approved
with no remaining actionable findings. No tutor validation is claimed.

The main orchestrator then stopped the QEMU guest, removed its overlay and
runtime metadata, destroyed all four ContainerLab nodes, removed both exact
bridges, and removed the temporary privileged validation helper. The
post-destroy audit found zero target containers, QEMU processes, taps, bridges,
listeners on ports 2401/4401/8644, runtime directories, generated ContainerLab
directory, capture/transaction files, or validation helper. The external base
image was preserved as intended.

## Limitations

- The probe covered one x86-64 OPNsense 26.1.6_2 base on KVM. Other releases,
  architectures, and hypervisors were not tested.
- One concentrator, two fixed peers, split routing, static PF policy, and
  selective revocation were probed. HA, roaming, DNS policy, MFA, scale,
  performance, and long-duration key lifecycle were not.
- Loopback root/`opnsense` management and serial telnet are disposable local
  training conveniences, not production controls.
- The requested `lab-tutor` surface is unavailable in the parent remediation
  workflow; no tutor validation is claimed.
